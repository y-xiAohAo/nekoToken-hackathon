# 开发起点

以下是从现有方案导出的实现顺序建议。最小 Godot 工程壳已创建并完成本地启动、Windows 导出；本文仍未替团队锁定玩法数值或分工。具体开发顺序以[最小游戏框架 Spec](../docs/minimal-framework-spec.md)为准。

## 先验证一个猜测周期

用一张灰盒网格实现移动、墙体遮挡、单台摄像头、沿固定相邻格路线折返的巡逻设备和一块可见单格踏板。先用可控的模拟 Agent 选择验证程序规则，再接模型。踏板只在移动实体从外进入时留下匿名激活记录，部署在实体脚下不触发；图示美术只作为布局参考，不直接等同可用游戏资产。

建议把世界状态、设备状态、报告、周期快照和各方记忆分开存储。设备ID对外不编码空间位置；助手只收到玩家文字和合法接口回执。城市系统不接收真实玩家坐标，命中检查留在程序中。

状态推进建议表示为：猜测周期内行动与定时上报 → 猜测刻推理（暂停）→ 命中后的回退/本轮失败，或未命中且本轮继续时的调度 → 下一猜测周期行动。联络会话在行动阶段触发，暂存并冻结现场；联络结束时先在暂停中校验、提交并同步合法改动，立即生效后再恢复行动；系统仍到正常上报边界才获知配置更新。联络与猜测刻推理必须互斥。若猜测刻玩家已满足通关条件，仍先猜测；未命中则本轮成功并跳过调度。

## 第一个可演示闭环

玩家沿两条可选路线接近交接核验装置；在联络点描述设备，让助手执行一项有效改动；完成现场操作并离开。中途发生批量上报，系统定位一次。展示一次局部回退与记忆保留，再展示下一轮系统凭历史报告改变一个合法配置。场景使用 Spec v0.42 的维护预演映射；首版不用门或规则性灯，踏板数量与布置待灰盒验证。

这只是验证切片。完整既定方案仍是4轮与3次共享玩家回退，不得为了切片悄悄改成最终只做一轮。

## 验收场景

1. 正常路径能完成核验装置操作并抵达出口；目击只产生报告，不立即失败。
2. 视野外或遮挡部分是未知；踏板激活不标明触发者，无激活不能当作玩家不在。踏板放置成功与否不依赖隐藏占位，模型不能通过回执试探坐标。
3. 联络和猜测刻推理时，移动、设备轨迹、踏板触发与猜测周期时间全部冻结；恢复后没有跳帧结算。
4. 助手离点操作、超额改动、非法设备参数被拒绝且不改变现场。
5. 系统定位未命中后只允许一次合规调度与新增，动作校验不能自行扩范围。
6. 局部回退真正删除该周期新增设施，恢复任务与联络状态，同时扣除一次共享回退；各方记忆保留并标明撤销分支。
7. 整轮重启重置现场和本轮任务，不清助手记忆，不补回玩家共享回退，4轮正确结算。
8. 非法命令不改变世界，也不能当作部署成功恢复行动。模型超时、持续无合法方案时是否取消部署或结束会话，需先定策略再实现；不能用自动跳过伪装成功，也不能把模拟返回称为真实推理。

优先用这些场景判断程序是否自洽。随后测量整场时长和干预价值，再讨论装饰、更多设施或复杂模型框架。
