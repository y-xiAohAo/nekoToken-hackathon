# 0001 · 将资料迁移仓库整理为开发仓库

日期：2026-11-27。状态：本轮仓库维护采用；具体游戏技术和玩法未新增决策。

## 问题

初始提交完整保留迁移资料，但 `tmp/` 已跟踪 149 个历史生成文件；普通校验要求本机附带 Python 包、Poppler 和 Node；每次编辑还会使迁移哈希清单失效。这些做法适合验证一份迁移包，不适合两人长期并行修改和从 Git 干净克隆。

## 采用的做法

1. 旧生成过程移动到 `archive/production/`，保留每个文件字节内容及旧、新路径映射。既有历史重复文件保留；不改写旧提交、不丢弃原始证据。
2. 旧清单与验证脚本作为初始快照归档。开发修改由 Git、链接检查、仓库内容检查和回归测试记录，不再要求每次改文档都重建整仓哈希清单。
3. 游戏未来落在 `game/`；现行 Spec、机制和原文入口保持原路径。工程文档单独放 `docs/`。
4. 使用 `main` 加短期分支、PR 和 squash 的轻量流程。先落实可运行的 CI，不预设多层审批、长期发布分支或强制的人员分工。
5. 历史材料保留字节；新代码和工程文档使用 LF。新临时产物、运行时、依赖缓存与凭据不入库；Godot 的源文件和 UID 元数据正常入库。

## 代价与边界

旧生成器需要按原目录恢复或在旧提交中复现，不能将归档路径当作原始执行目录。检查仅针对仓库和维护脚本；Godot 版本尚未锁定，当前不添加伪造的游戏构建成功标记。CI 未连接真实模型，也不验证账号余额或赛事提交规则。

本次不安装 Git LFS、不更改仓库可见性、不邀请协作者、不设必须由特定人员批准的门禁。2026-11-27 通过 GitHub API 复核，仓库当前为公开状态，与创建时记录的私有状态不同；本轮维持复核时的设置并更新现行说明。服务器端分支保护与团队授权需按实际账号能力另行落实。

## 验收

- 归档迁移内容哈希保持不变；现行 Spec 和机制正文保持不变。
- 不依赖 `tools/` 的干净克隆能运行检查与单元测试。
- 缺失链接、越界路径、意外跟踪缓存、明确凭据模式和超限文件能使检查失败。
- Windows 与 Linux CI 使用相同检查命令。完成状态以具体工作流结果为准。
