# 最小游戏框架 Spec（讨论稿）

更新：2026-11-27。本文是基础框架的开发基线，规定从工程壳开始的模块边界与首批验收；关卡布局、数值平衡和 Agent 动作授权仍以 [现行设计 Spec](../PRELIMINARY_DESIGN_SPEC.md) 和 [机制基准](../侦测定位_机制草案.md) 为准。后续玩法决定若改变框架契约，先修订本文再实现。

## 1. 目标与完成范围

首个框架应能在一张灰盒地图上运行一个猜测周期：玩家与设备按模拟时间行动，摄像头和机器人逐感知步记录视觉观察，踏板按进入事件记录激活，所有设备按上报周期同步提交原始记录；累计固定批数后暂停，由模拟系统 Agent 提交一次位置猜测，游戏程序校验。随后证明运行时地图和设备能通过受校验命令变更，并可由猜测周期起点快照恢复。

框架还须留出两个角色隔离的 Agent 接口、游戏内联络窗口及真实服务桥接位置。首个检查点不要求真实 DeepSeek 调用、四轮结算、正式地图、美术或完整动作权限。任何模拟响应都要明确标为模拟。

## 2. 时间与阶段

| 层级 | 定义 | 权威方 |
| --- | --- | --- |
| 整场 | 四轮及整场共享的局部回退次数 | `GameSession` |
| 一轮 | 从入场到成功或最终失败，包含若干猜测周期 | `GameSession` |
| 猜测周期 | 相邻两次猜测之间的模拟行动时间；首个周期从本轮开始到首次猜测。每周期含固定数量的上报周期 | `GameSession` |
| 上报周期 | 固定模拟时间窗；结束时所有上报载体同步提交各自在本周期内的结构化记录 | 报告调度器 |
| 感知步 | 摄像头或机器人执行一次离散视觉观察的时刻；踏板另按进入事件触发，具体视觉频率是原型参数 | 设备感知逻辑 |
| 物理步 | Godot 移动、碰撞等固定更新步；感知频率可独立配置，不预设每个物理步都要感知 | Godot 物理循环 |

`simulation_tick` 是游戏模拟时钟的唯一来源。联络、猜测、调度及回退选择期间，模拟时钟和所有依赖它的设备计时均冻结；真实等待时间只用于界面和服务超时。只有猜测刻能请求系统 Agent 猜测，设备观察与目标操作本身不触发额外猜测。固定批数与间隔由可替换的原型配置提供，不能把试验值写成已确认玩法值。

连续移动中的玩家在每个物理刻都有确定的浮点世界坐标；需要统一的是边界处各系统读取坐标的时机。以相邻上报边界 `t` 与 `t+1` 为例，`[t, t+1)` 内的感知记录与目标操作事件属于从 `t` 开始的上报周期；恰在 `t+1` 发生的记录属于下一上报周期。物理推进到 `t+1` 后先写回玩家坐标，再封存 `[t, t+1)` 的记录；若该边界也是猜测刻，猜测使用此时冻结的坐标，不读取 Agent 回复到达后的坐标。实现使用整数步编号判定归属，不以浮点相等比较决定边界。

玩家在联络点的暂停与系统猜测暂停互斥。联络结束时，在模拟仍冻结的情况下校验并原子提交助手的获准改动，完成必要的设备同步后立即生效，再恢复行动；不等待下一上报边界。失败保留原世界并继续暂停，不得当作部署成功放行。允许明确选择保持现状后结束部署；该选择不改变世界或消耗设备改动额度，但不撤销已使用的联络会话，也不能由失败自动触发。系统 Agent 仍在下一次统一上报获知获准的配置更新。猜测刻一律暂停并禁止玩家操作；若同时满足通关条件，仍先完成本次猜测及命中校验：未命中则本轮成功并跳过调度，命中则进入命中和回退选择。系统猜错且本轮继续时的调度在下一猜测周期起点生效。上述顺序由 `GameSession` 调度；同一参数按实际成功提交的先后覆盖，不再维护等待上报边界的玩家配置队列。

时机修订追溯（2026-11-27）：早期方案曾采用“下一上报周期边界生效”；考虑到联络后的即时干预收益，现改为联络结束即刻生效。该时序已由模块 1 的阶段入口和模块 2 的世界命令提交路径落实。报告仍统一上传；配置执行时点与系统获知时点分开。

阶段至少区分 `ACTION`、`CONTACT_PAUSED`、`GUESS_PAUSED`、`DISPATCH_PAUSED`、`RESET_CHOICE`、`ROUND_END`。阶段变更只能由 `GameSession` 发起；非法阶段的输入与迟到模型回复不得改变世界。首批代码可先实现 `ACTION` 与 `GUESS_PAUSED`，但阶段枚举和转换检查须可扩展。

## 3. 模块与依赖方向

```text
Main
├─ GameSession：阶段、时钟、上报/猜测调度、权限检查、快照
├─ World：地图、玩家、设备、目标和出口的运行时实例
├─ AgentGateway：模拟接口；后续替换为真实桥接
└─ UI：调试状态；后续加入游戏内联络窗口

设备感知 → 原始观察记录 → 本周期上报包 → 系统 Agent 视图 → AgentGateway
Agent 提议 → 候选世界校验及必要派生状态准备 → 原子提交并完成同步 → 恢复模拟
```

`World` 不调用模型，`AgentGateway` 不直接修改节点或地图，`UI` 不裁决规则。`GameSession` 负责接受经校验的命令并调用世界变更入口。场景树负责显示与物理，规则状态须有明确的数据表示；不能把一个节点是否存在当成设备存在的唯一事实。首版不使用覆盖所有玩法的全局 Autoload；可复用组件按实际需要建立。

Godot 物理步结束时，玩家的权威位置与运动状态写回 `WorldState`；感知与命中校验只读取该步已提交的状态。地图/设备命令只能在定义好的模拟边界提交，派生系统完成同步后才恢复后续模拟步。进入模拟 Agent 猜测前，先固定双角色隔离的请求/响应契约：角色视图、`round_id` / `branch_id` / `guess_cycle_id` / 请求 ID、结构化动作与执行回执。模拟端和真实服务端遵守同一契约；传输、重试和超时策略可后置。

## 4. 权威状态与完整快照

| 数据 | 包含内容 | 局部回退 |
| --- | --- | --- |
| `LevelTemplate` | 基础网格、初始墙/通路、初始摄像头/机器人/踏板、目标装置、联络点和出口定义及坐标转换配置；不预设运行时 ID | 不变；作为恢复基底 |
| `WorldState` | 当前可走格、玩家位置与运动状态、统一实体注册表、位置/参数/扫描相位、巡逻路线/当前段/进度/折返方向、踏板占用基线、联络点可用状态与目标进度等 | 恢复猜测周期起点 |
| `CycleState` | 模拟时钟、上报周期编号、已累计批数、待上传的逐步记录、当前分支有效报告、待结算事件及使用时的随机状态 | 恢复猜测周期起点 |
| `RunProgress` | 当前轮次、整场剩余回退、已结算轮次 | 按现行规则保留，不随局部快照恢复 |
| `AgentHistory` | 两名 Agent 各自实际收到的信息、回复与执行回执、分支标记 | 保留；撤销分支标为历史 |

世界在初始化时为模板中的实体分配运行时 ID，后续新增设备也由世界分配；ID 在实例存续、移动和改参期间保持稳定。快照保留现有 ID 与明确字段，不依赖场景树节点路径或浅拷贝。恢复时先恢复地图拓扑与设备注册表，恢复玩家与机器人位置及设备运行状态后，再同步显示、碰撞和设备检测依赖，全部就绪后才恢复模拟计时。新分支产生新的 `branch_id`；异步请求还要携带 `round_id`、`guess_cycle_id` 和请求 ID。回复标识与当前状态不符即作废。

猜测未命中且本轮继续时，按“结束本次猜测 → 系统在暂停阶段提出调度 → 校验候选世界并准备必要的派生状态 → 原子提交并完成必要的设备同步 → 初始化下一猜测周期的计时与记录缓冲 → 保存周期起点快照 → 恢复行动”的顺序执行。命中后若玩家选择局部回退，恢复的是当前猜测周期已保存的起点快照，不再进行一次调度。整轮重启以同一个基础关卡模板建立新轮，并应用该轮获准的初始配置；两类 Agent 的历史与整场回退余额按现行规则保留。动态拓扑能否成为轮间合法配置仍是玩法待定项。

## 5. 地图与设备的动态变更能力

现行场景是同层方格、连续移动。地图的**权威表示**是网格拓扑和运行时覆盖状态：墙、地面及可通行关系由数据决定；首版不建立门或规则性灯实体。Godot 的图块、碰撞形状和路径查询是由该状态更新的表现与派生结果。摄像头、机器人和可见踏板有稳定运行时 ID、位置及各自受校验的参数。玩家与移动中的机器人使用连续世界坐标；拓扑操作和踏板位置使用地图格坐标，并由统一转换规则连接二者。

摄像头、机器人、踏板、目标装置、联络点和出口使用统一注册表；类型字段与操作权限分开。系统 Agent 不得动态新增、移除或移动目标装置、联络点和出口，游戏规则仍可更新其目标进度或使用状态。踏板每个覆盖一格，同格最多一块，不能与墙或阻挡设施重叠；可与天花板摄像头共格，玩家和机器人占位不影响其放置合法性。目标装置与联络点阻挡通行，玩家靠近后按指定键交互；出口有实体体积，条件不足时阻挡，条件满足后触碰产生通关条件，不需按键。出口不直接结算，仍交给 `GameSession` 保证猜测优先。当前所有挡路的静态内容统一按实心处理，同时挡视线；移动碰撞和视线遮挡分别查询，由同一实心类型规则给出结果，不开放两个独立的 Agent 参数。出口达到条件不表示先清除体积或遮挡。墙装与顶装摄像头使用同一种类型，以安装方式和锚点区分；允许朝向范围、配置扫描区间、瞬时视野角分别表达，具体角度不在本模块自定。

机器人使用上下左右相邻整数格对应的格心序列，禁止斜相邻；空路线非法，单点表示驻守，多点沿原路线折返，不在行动中自动重新寻路。默认视野为以自身为圆心、受墙体及实心设施遮挡的圆形，半径由关卡配置；本模块只存储该类型与参数，不实现视觉检测。获准换路在联络结束或猜错后调度完成时生效；程序锁定机器人暂停时的连续位置作为真实起点。若停在两个格心之间，先完成当前段，再接以该段终点为首点的新路线；该衔接只执行一次，不加入往复路线。位于格心时，新路线直接从该格心开始。衔接段及往复路线均须在候选地图上合法，不要求末端与首端相邻，也不允许换路使机器人瞬移。单点新路线也须遵守上述起点与衔接规则，不能通过驻守命令瞬移；这些规则不开放助手换路权限。

框架需容纳下列有类型的变更提议，首批实现不必同时开放全部给 Agent：

| 命令类别 | 框架必须表达的变化 |
| --- | --- |
| `SetMapCell` | 在合法格增删墙体或改变通路；不含任意形状绘制 |
| `AddDevice` / `RemoveDevice` | 增删一台有类型、有世界分配 ID 的设备，包括踏板 |
| `MoveDevice` | 改变摄像头或踏板等设备位置 |
| `SetDeviceParameter` | 改变摄像头朝向/扫描范围等已声明且有界的参数 |
| `SetPatrolPath` | 更换机器人相邻整数格的折返路线；锁定真实起点、完成当前段后衔接，不瞬移 |

唯一入口按以下顺序处理一组命令：检查请求属于当前分支和阶段；检查角色权限、次数及参数；在候选副本上检查地图边界、目标 ID、静态合法位置和路径有效性；候选数据和必要的派生同步准备全部通过后，才对外提交新世界并返回逐项可追溯的执行回执；成功后才能结束暂停。失败不得留下半张新地图。拓扑变更保守拒绝与玩家/设备当前占位冲突或使现有巡逻路径失效的情况，不自动给机器人重新寻路。踏板不阻挡移动：其增删、移动不得以玩家或机器人隐藏占位为拒绝条件，回执也不得泄漏该信息。是否必须始终保留玩家到目标及出口的通路，属于待定玩法策略；验证入口应支持此规则，而不能由模型绕开。

世界变更后，所有设备的后续检测都必须读取已提交的同一份权威状态。踏板的格位置和一格覆盖、摄像头的安装与扫描参数、机器人的路线与进度都属于对象自身的数据；显示节点或检测系统不能另存一套可独立修改的权威参数。直接读取最新状态的检测不需要额外刷新；若使用碰撞形状、预计算视野等派生缓存，须在恢复模拟前同步。拓扑变更可能影响未直接改参的设备，也必须更新其遮挡依赖。

同步不等于重置所有设备：未受命令影响的扫描相位、巡逻进度与踏板进入基线应保持。仅新增或移动踏板时，以部署瞬间的占用情况初始化进入判定：已在范围内的实体须先离开再进入，部署动作不生成激活。踏板历史记录保存事件当时的权威位置，不能在上传时重新读取已移动设备的位置。固定巡逻不要求导航缓存；若最终候选路线或衔接段无效，拒绝该批变更。

模块 2 已实现权威数据、校验、原子提交及同步入口，用测试替身验证同步结果与阶段放行；实际碰撞、视觉检测、踏板进入检测和移动控制由后续模块接入。当前有设备数据模型，没有对应场景行为，不能把接口测试当作真实设备同步已经通过。同步准备失败保持原世界；激活意外失败锁住部署入口并保持暂停。接口和限制见模块 2 Feature Spec，没有增加通用场景回滚框架。

**能力与授权分离。**玩家助手的首版候选是摄像头朝向／扫描区间等有界参数。系统 Agent 已获准在合法调度窗口提议增删、移动踏板，具体额度与合法区域待定。本段不授权任一 Agent 增删墙体、移动摄像头或改机器人路径，也不授权玩家助手操作踏板。其它动作开放、调用阶段与额度应在权限表中逐项确定。

## 6. 观察、上报与 Agent 视图

每条视觉观察记录至少有 `round_id`、`branch_id`、`guess_cycle_id`、`report_cycle_id`、`device_id`、`sense_tick`、结果类型，以及结果对应的地图坐标区域。正面观察上报测得的小范围 D；可靠未检测到上报该感知步实际覆盖的 R；无法判断保留原因。踏板从外进入时另产生激活记录，保存踏板 ID、事件模拟刻及当时的位置，不标明触发者，不直接当作玩家目击；无触发也不是可靠无人记录。记录不包含可直接供系统 Agent 读取的玩家真实位置。目标装置的操作事件另有发生时刻和装置 ID。

每个上报周期结束时，生成按设备归属、事件时序排列的上报包，恰好包含本周期视觉观察、踏板激活及目标操作事件。相同记录也分别保留；游戏程序不在周期内或跨周期压缩、合并、去重。没有可靠视觉观察时仍产生该周期的上报边界；本批可能只有踏板或目标事件，也可能为空或包含明确的未知观察，不改变猜测机会的固定节奏。踏板部署或移动不产生即时触发和额外猜测。玩家助手的配置改动在联络结束时立即生效，获准配置更新仍随下一次统一上报交付系统 Agent。一批可含变更前后的记录，各条保留事件发生时的实际观察区域或踏板位置；不得在上传时根据最新配置重新计算旧事实。后续报告模块须据此确定必要的配置关联字段，不把完整命令审计或联络来源直接透传给 Agent。交付信息不附带联络点来源或玩家位置字段。

系统 Agent 视图含静态地图、已授权的设备配置及已收到的报告；不含玩家真实坐标。玩家助手视图含玩家文字、获准工具回执和自身历史；不含地图、画面或系统内部状态。两种视图分别由游戏程序构建，不能把完整状态交给模型后仅靠提示词限制读取。

## 7. 实施检查点

1. **工程壳与版本。**建立 `game/project.godot`、最小 `Main/World/UI`，记录本分支验证过的 Godot 小版本及启动/导出命令；团队最终小版本待协作确认。
2. **规则内核与接口契约。**已定义 `CycleState`、整数模拟时钟、阶段转换、上报边界和双角色基础请求/响应结构；`WorldState` 与实际场景位置写回留给检查点 3 之后。
3. **世界与命令入口。**建立网格/设备权威数据、世界分配的稳定运行时 ID、候选副本校验和场景同步入口；以墙格、摄像头、机器人和可新增/移动踏板验证。非法命令不产生部分变化，踏板放置回执不依赖隐藏占位。
4. **感知与上报。**一台模拟设备逐感知步产出三条相同记录，两次同步上报各自保留原始条目；按角色构建隔离视图，暂停时计数不前进。
5. **模拟 Agent 与一个猜测周期。**沿用第 2 步契约累计固定批数后暂停，只产生一次模拟猜测，由游戏校验命中；此步不需要真实模型。
6. **快照与分支。**在猜测周期起点保存完整快照；中途改变墙格、踏板等设备及待上传记录后恢复，确认全部回到起点。整场回退次数和两名 Agent 已接触的历史按规则保留；旧分支回复不能修改新分支。
7. **联络与剩余动态命令。**增加玩家助手 UI、模拟动作和联络点状态；按权限表逐项开放已受校验的世界命令，接入联络结束即刻提交和同步成功后恢复行动的流程。
8. **真实桥接与整场。**明确超时、非法输出及断线处理后，再接本地或托管服务与真实模型，并验证四轮及两类 RESET。密钥不进入 Godot 工程、Git 或测试日志。

每项检查点都须有实际运行证据；自动化测试只覆盖真实风险，不用空测试替代运行验证。首个可玩切片还需按设计 Spec 验证目标操作、撤离、四轮和两类 RESET。

## 8. 尚待定案，不能由框架偷偷决定

- 感知频率、上报周期长度、每个猜测周期的批次数、D 的范围与原始记录量；无压缩规则意味着接真实模型前必须测量输入规模和等待时间。
- 系统 Agent 踏板增删／移动的额度与合法区域；其它动态世界命令对双方的开放阶段、次数、合法区域、是否要求始终可达；拓扑变更何时进入两名 Agent 各自可见的地图视图。首版路径失效的拓扑变更被拒绝。
- 模型超时、空回复、非法动作的重试、默认动作和玩家反馈。

以上未定项分阶段处理：感知频率和批次数在检查点 4 作为可替换原型配置确定；拓扑可见性、动作权限和可达性策略在开放相应 Agent 命令前确定；模型异常策略在检查点 8 前确定。它们不阻止检查点 1–2，也不允许实现时暗中将试验值当作已定玩法。
