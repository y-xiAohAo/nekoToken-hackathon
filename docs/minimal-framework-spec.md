# 最小游戏框架 Spec（讨论稿）

更新：2026-11-27。本文是基础框架的开发基线，规定从工程壳开始的模块边界与首批验收；关卡布局、数值平衡和 Agent 动作授权仍以 [现行设计 Spec](../PRELIMINARY_DESIGN_SPEC.md) 和 [机制基准](../侦测定位_机制草案.md) 为准。后续玩法决定若改变框架契约，先修订本文再实现。

## 1. 目标与完成范围

首个框架应能在一张灰盒地图上运行一个猜测周期：玩家与设备按模拟时间行动，设备逐感知步记录观察，所有设备按上报周期同步提交原始记录；累计固定批数后暂停，由模拟系统 Agent 提交一次位置猜测，游戏程序校验。随后证明运行时地图和设备能通过受校验命令变更，并可由猜测周期起点快照恢复。

框架还须留出两个角色隔离的 Agent 接口、游戏内联络窗口及真实服务桥接位置。首个检查点不要求真实 DeepSeek 调用、四轮结算、正式地图、美术或完整动作权限。任何模拟响应都要明确标为模拟。

## 2. 时间与阶段

| 层级 | 定义 | 权威方 |
| --- | --- | --- |
| 整场 | 四轮及整场共享的局部回退次数 | `GameSession` |
| 一轮 | 从入场到成功或最终失败，包含若干猜测周期 | `GameSession` |
| 猜测周期 | 相邻两次猜测之间的模拟行动时间；首个周期从本轮开始到首次猜测。每周期含固定数量的上报周期 | `GameSession` |
| 上报周期 | 固定模拟时间窗；结束时所有上报载体同步提交各自在本周期内的结构化记录 | 报告调度器 |
| 感知步 | 设备执行一次离散观察并形成一条记录的时刻；具体频率是原型参数 | 设备感知逻辑 |
| 物理步 | Godot 移动、碰撞等固定更新步；感知频率可独立配置，不预设每个物理步都要感知 | Godot 物理循环 |

`simulation_tick` 是游戏模拟时钟的唯一来源。联络、猜测、调度及回退选择期间，模拟时钟和所有依赖它的设备计时均冻结；真实等待时间只用于界面和服务超时。只有猜测刻能请求系统 Agent 猜测，设备观察与目标操作本身不触发额外猜测。固定批数与间隔由可替换的原型配置提供，不能把试验值写成已确认玩法值。

连续移动中的玩家在每个物理刻都有确定的浮点世界坐标；需要统一的是边界处各系统读取坐标的时机。以相邻上报边界 `t` 与 `t+1` 为例，`[t, t+1)` 内的感知记录与目标操作事件属于从 `t` 开始的上报周期；恰在 `t+1` 发生的记录属于下一上报周期。物理推进到 `t+1` 后先写回玩家坐标，再封存 `[t, t+1)` 的记录；若该边界也是猜测刻，猜测使用此时冻结的坐标，不读取 Agent 回复到达后的坐标。实现使用整数步编号判定归属，不以浮点相等比较决定边界。

玩家在联络点的暂停与系统猜测暂停互斥。玩家助手提交的合法配置改动先排队，在下一上报周期起点、前一周期封包后生效；系统 Agent 在该次统一上报获知更新后的配置。猜测刻一律暂停并禁止玩家操作；若同时满足通关条件，仍先完成本次猜测及命中校验。猜测未命中则本轮成功，跳过调度；猜测命中则进入命中和回退选择。系统猜错且本轮继续时的调度只在下一猜测周期起点生效。上述顺序由 `GameSession` 调度，不依赖各节点信号的偶然触发顺序。若玩家待生效改动与系统调度涉及同一参数，按提交到世界的先后顺序覆盖；该边界先应用玩家改动，再应用系统调度，并给双方可追溯的回执。

阶段至少区分 `ACTION`、`CONTACT_PAUSED`、`GUESS_PAUSED`、`DISPATCH_PAUSED`、`RESET_CHOICE`、`ROUND_END`。阶段变更只能由 `GameSession` 发起；非法阶段的输入与迟到模型回复不得改变世界。首批代码可先实现 `ACTION` 与 `GUESS_PAUSED`，但阶段枚举和转换检查须可扩展。

## 3. 模块与依赖方向

```text
Main
├─ GameSession：阶段、时钟、上报/猜测调度、权限检查、快照
├─ World：地图、玩家、设备、目标和出口的运行时实例
├─ AgentGateway：模拟接口；后续替换为真实桥接
└─ UI：调试状态；后续加入游戏内联络窗口

设备感知 → 原始观察记录 → 本周期上报包 → 系统 Agent 视图 → AgentGateway
Agent 提议 → 权限与世界约束校验 → 原子世界变更 → 画面/碰撞/遮挡/导航刷新
```

`World` 不调用模型，`AgentGateway` 不直接修改节点或地图，`UI` 不裁决规则。`GameSession` 负责接受经校验的命令并调用世界变更入口。场景树负责显示与物理，规则状态须有明确的数据表示；不能把一个节点是否存在当成设备存在的唯一事实。首版不使用覆盖所有玩法的全局 Autoload；可复用组件按实际需要建立。

Godot 物理步结束时，玩家的权威位置与运动状态写回 `WorldState`；感知与命中校验只读取该步已提交的状态。地图/设备命令只能在定义好的模拟边界提交，派生系统完成同步后才恢复后续模拟步。进入模拟 Agent 猜测前，先固定双角色隔离的请求/响应契约：角色视图、`round_id` / `branch_id` / `guess_cycle_id` / 请求 ID、结构化动作与执行回执。模拟端和真实服务端遵守同一契约；传输、重试和超时策略可后置。

## 4. 权威状态与完整快照

| 数据 | 包含内容 | 局部回退 |
| --- | --- | --- |
| `LevelTemplate` | 基础网格、初始墙/门/通路、初始设备定义、稳定 ID | 不变；作为恢复基底 |
| `WorldState` | 当前可走格与门状态、玩家位置与运动状态、设备清单/位置/参数/扫描相位/巡逻进度、联络点可用状态、目标进度、照明与冷却等 | 恢复猜测周期起点 |
| `CycleState` | 模拟时钟、上报周期编号、已累计批数、待上传的逐步记录、当前分支有效报告、待结算事件/命令及使用时的随机状态 | 恢复猜测周期起点 |
| `RunProgress` | 当前轮次、整场剩余回退、已结算轮次 | 按现行规则保留，不随局部快照恢复 |
| `AgentHistory` | 两名 Agent 各自实际收到的信息、回复与执行回执、分支标记 | 保留；撤销分支标为历史 |

快照使用稳定设备 ID 和明确字段，不依赖场景树节点路径或浅拷贝。恢复时要先恢复地图拓扑与设备注册表，再同步视觉、碰撞、遮挡、照明和导航，最后恢复玩家与计时。新分支产生新的 `branch_id`；异步请求还要携带 `round_id`、`guess_cycle_id` 和请求 ID。回复标识与当前状态不符即作废。

猜测未命中且本轮继续时，按“结束本次猜测 → 系统在暂停阶段提出调度 → 校验并一次性提交 → 同步碰撞、遮挡、照明和导航 → 初始化下一猜测周期的计时与记录缓冲 → 保存周期起点快照 → 恢复行动”的顺序执行。命中后若玩家选择局部回退，恢复的是当前猜测周期已保存的起点快照，不再进行一次调度。整轮重启以同一个基础关卡模板建立新轮，并应用该轮获准的初始配置；两类 Agent 的历史与整场回退余额按现行规则保留。动态拓扑能否成为轮间合法配置仍是玩法待定项。

## 5. 地图与设备的动态变更能力

现行场景是同层方格、连续移动。地图的**权威表示**是网格拓扑和运行时覆盖状态：墙、地面、门及可通行关系由数据决定；Godot 的图块、碰撞形状和路径查询是由该状态更新的表现与派生结果。设备另有稳定 ID、位置与参数。玩家和设备可使用连续世界坐标；拓扑操作使用地图格坐标，并由统一转换规则连接二者。

框架需容纳下列有类型的变更提议，首批实现不必同时开放全部给 Agent：

| 命令类别 | 框架必须表达的变化 |
| --- | --- |
| `SetMapCell` | 在合法格增删墙体或改变通路；不含任意形状绘制 |
| `SetDoorState` | 开/关或启用/移除具有稳定 ID 的门 |
| `AddDevice` / `RemoveDevice` | 增删一台有类型、有稳定 ID 的设备 |
| `MoveDevice` | 改变摄像头等设备位置 |
| `SetDeviceParameter` | 灯状态、摄像头朝向/扫描范围等可声明参数 |
| `SetPatrolPath` | 更换机器人的有效路径点与巡逻进度处理方式 |

唯一入口按以下顺序处理一组命令：检查请求属于当前分支和阶段；检查角色权限、次数及参数；在候选副本上检查地图边界、目标 ID、碰撞位置和路径有效性；全部通过后一次性提交并刷新派生系统；返回逐项可追溯的执行回执。失败不得留下半张新地图。首个灰盒切片保守拒绝与玩家/设备当前占位冲突或使现有巡逻路径失效的拓扑变更。是否必须始终保留玩家到目标及出口的通路，属于待定玩法策略；验证入口应支持此规则，而不能由模型绕开。

改变墙、门或通路后，至少使玩家碰撞、设备视线遮挡、照明覆盖和机器人路径查询与新地图一致；若既有机器人路径失效，应按明确策略拒绝变更或重算路径，不能继续穿墙。Godot 的 `TileMapLayer` 能更新网格单元，`AStarGrid2D` 能调整格点通行性；具体渲染实现不应成为规则状态的唯一来源。[TileMapLayer](https://docs.godotengine.org/en/stable/classes/class_tilemaplayer.html)、[AStarGrid2D](https://docs.godotengine.org/en/stable/classes/class_astargrid2d.html)

**能力与授权分离。**当前玩法给玩家助手的首版候选仍主要是灯和摄像头部分参数；系统 Agent 在猜错后的受限调度及轮间配置也仍受现行规则约束。本段不授权任一 Agent 增删墙体、改门、删设备、移动摄像头或改机器人路径。具体动作开放、调用阶段、合法区域和额度，应在后续权限表中逐项确定。

## 6. 观察、上报与 Agent 视图

每条观察记录至少有 `round_id`、`branch_id`、`guess_cycle_id`、`report_cycle_id`、`device_id`、`sense_tick`、结果类型，以及结果对应的地图坐标区域。正面观察上报测得的小范围 D；可靠未检测到上报该感知步实际覆盖的 R；无法判断保留原因。观察记录不包含可直接供系统 Agent 读取的玩家真实位置。目标装置的操作事件另有发生时刻和装置 ID。

每个上报周期结束时，生成按设备归属、感知顺序排列的上报包，恰好包含本周期记录。相同记录也分别保留；游戏程序不在周期内或跨周期压缩、合并、去重。没有可靠观察时仍产生该周期的上报边界，记录可为空或为明确的未知观察，不改变猜测机会的固定节奏。玩家助手的配置改动先排队：下一上报边界封存旧周期记录后，改动在新上报周期起点生效，并随该次统一上报交付系统 Agent；旧周期记录仍按产生时的设备配置解释。交付信息不附带联络点来源或玩家位置字段。

系统 Agent 视图含静态地图、已授权的设备配置及已收到的报告；不含玩家真实坐标。玩家助手视图含玩家文字、获准工具回执和自身历史；不含地图、画面或系统内部状态。两种视图分别由游戏程序构建，不能把完整状态交给模型后仅靠提示词限制读取。

## 7. 实施检查点

1. **工程壳与版本。**建立 `game/project.godot`、最小 `Main/World/UI`，记录本分支验证过的 Godot 小版本及启动/导出命令；团队最终小版本待协作确认。
2. **规则内核与接口契约。**定义 `WorldState` / `CycleState`、整数模拟时钟、阶段转换、同一步事件排序和双角色 Agent 请求/响应结构；用最小场景验证位置写回与暂停边界。
3. **世界与命令入口。**建立网格/设备权威数据、稳定 ID、候选副本校验和场景同步；先实现一扇门和一台可新增/移动设备。非法命令不产生部分变化。
4. **感知与上报。**一台模拟设备逐感知步产出三条相同记录，两次同步上报各自保留原始条目；按角色构建隔离视图，暂停时计数不前进。
5. **模拟 Agent 与一个猜测周期。**沿用第 2 步契约累计固定批数后暂停，只产生一次模拟猜测，由游戏校验命中；此步不需要真实模型。
6. **快照与分支。**在猜测周期起点保存完整快照；中途改变门、设备及待上传记录后恢复，确认全部回到起点。整场回退次数和两名 Agent 已接触的历史按规则保留；旧分支回复不能修改新分支。实现 `SetMapCell` 后，再增加墙体变更及墙体回退验收。
7. **联络与剩余动态命令。**增加玩家助手 UI、模拟动作和联络点状态；按权限表逐项开放动作，并补齐墙格、设备移除及巡逻路径等命令。
8. **真实桥接与整场。**明确超时、非法输出及断线处理后，再接本地或托管服务与真实模型，并验证四轮及两类 RESET。密钥不进入 Godot 工程、Git 或测试日志。

每项检查点都须有实际运行证据；自动化测试只覆盖真实风险，不用空测试替代运行验证。首个可玩切片还需按设计 Spec 验证目标操作、撤离、四轮和两类 RESET。

## 8. 尚待定案，不能由框架偷偷决定

- 感知频率、上报周期长度、每个猜测周期的批次数、D 的范围与原始记录量；无压缩规则意味着接真实模型前必须测量输入规模和等待时间。
- 系统 Agent 与玩家助手可提出的动态世界命令、阶段、次数、合法区域、是否要求始终可达及路径失效策略；拓扑变更何时进入两名 Agent 各自可见的地图视图。
- 模型超时、空回复、非法动作的重试、默认动作和玩家反馈。

以上未定项分阶段处理：感知频率和批次数在检查点 4 作为可替换原型配置确定；拓扑可见性、动作权限和可达性策略在开放相应 Agent 命令前确定；模型异常策略在检查点 8 前确定。它们不阻止检查点 1–2，也不允许实现时暗中将试验值当作已定玩法。

## 9. 开发准入

检查点 1 工程壳已用 Godot 4.7.2 stable 本地启动并导出 Windows 构建；检查点 2 规则内核已实现并有 75 条本地 headless 契约断言，证据见 [模块 0 Spec](features/2026-11-27_14-22_module-0-project-shell.md)、[模块 1 Spec](features/2026-11-27_14-22_module-1-rule-kernel.md) 和 [游戏工程说明](../game/README.md)。模块 1 的内部时序内核可继续供下游开发；严格 Agent payload DTO 与猜测结果校验仍须在真实 AgentGateway 前完成。模块 2 应先围绕权威世界状态、拓扑、设备注册表和原子动态命令形成独立 Feature Spec。完整玩法数值和关卡布局无需先定。
