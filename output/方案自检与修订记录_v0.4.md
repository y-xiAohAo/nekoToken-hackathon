# 《请本人到场》方案自检与修订记录

> 历史修订记录：下文的关灯与照明讨论只解释旧版问题，不代表现行规则。以 [Spec v0.42](../PRELIMINARY_DESIGN_SPEC.md) 和 [机制 v0.23](../侦测定位_机制草案.md) 为准。

日期：2026-11-14。检查对象为v0.3方案正文、玩法框图、地图标注、设计Spec与机制记录；修订产物为 [v0.4可编辑稿](archive/submissions/AI_PLAY_72H_预赛方案_v0.4.md)及 [v0.4 PDF](archive/submissions/AI_PLAY_72H_预赛方案_v0.4.pdf)。本次是文档和规则对照检查，没有开展游戏试玩或模型效果测试。

## 发现的问题与处理

| 问题 | 原稿中的表现 | 本次处理 |
| --- | --- | --- |
| 远处关灯不一定覆盖维修 | 在入口联络后就短时关电机灯，随后还要走到维修区，没有说明时间是否足够。 | 重写例子：先只调整摄像头，不提前关灯，说明关灯窗口可能在抵达前消耗。 |
| 地图信息来源不清 | 采用跟随视角后，玩家却像在入口处直接看见远处电机、机器人和监控。 | 增加“先观察、再回联络点”；对话把机器人位置说成刚才的观察，恢复后仍要核对。 |
| 两次改动像为凑额度 | 同时转摄像头和关闭同一区域灯，没有解释各自处理哪个观察来源。 | 示例只改一项，明确取舍理由。允许优秀助手用少量改动解决问题，不为展示能力强行用满。 |
| 中间代号妨碍阅读 | A、C4、L6、M1、N在正文密集出现，联络点C又容易与摄像头混淆。 | 用入口联络点、维修电机、维修区摄像头等名称。只在展示接口对应关系时保留一个设备号。 |
| “系统”指代两种主体 | 城市AI和执行判定的程序都被简称为系统，容易误以为敌方直接知道命中或真实坐标。 | 全文固定为“城市系统”和“游戏程序”，判断与校验分开。 |
| 固定形状不等于限制面积 | 若只写形状固定而不约束大小，无法排除城市系统提交覆盖全图的范围。 | 首版方案写为范围大小受程序限制；具体形状、尺寸仍未定，5×5格不升格为正式参数。 |
| 照明与扫描可能被误读 | 关一盏灯未必使重叠照明的格子变暗；整体摆动区间也不是瞬时完整视野。 | 在设施表中补明两条区别；灯、摄像头和机器人均不独立决策。 |
| 额度似乎能积攒到后面 | “把关灯机会留给维修”可能被读成未用额度可跨点转存。 | 明确各点独立，不写成整轮共享资源；保留同次会话内的改动取舍。 |
| 外部Agent的聊天限制承诺过强 | 游戏可以限制自身窗口，不能强制计数用户在外部软件里的所有聊天。 | 分开游戏内消息限制与接口有效提交额度；离点后的设备改动由接口拒绝。 |
| 回退漏写新增设施 | 一处写恢复全部现场，另一处又把是否恢复新增设施列为待定。 | 依既定现场恢复原则，将设备实例清单纳入起点记录；下一轮的具体初始化清单仍待细化。 |
| 回退和判负分支容易混看 | 原框图的“选择局部回退”同时连向恢复和失败，支路解释不够明确。 | 改成“是否使用回退”，区分使用与放弃／用尽；去掉泛指的“全局机会”。 |
| 10分钟的计时范围不清 | 四轮行动、联络、推理和局部回退都占现实时间，不能只算移动时间。 | 明确是整场体验目标，包含全部等待；不写成已达成时长。把模型调用试通提前到开发首阶段。 |
| 历史候选混入当前规则 | 长机制记录同时保留旧状态、旧额度提案和新决定，容易误把旧“待定”当成现行规则。 | 将v0.19整体留档，当前机制重写为v0.20；旧故事的阈值结局与永久求助账本不进入当前玩法。 |

## 文字与图示修订

按Humanizer-zh检查原文，保留事实、范围和未验证状态，修改具体的重复与歧义，不使用检测器分数衡量效果。

- 正文与表格的中间代号出现次数从21次降到2次，均为同一个设备号，供说明接口对应关系。统计不含图片路径、版本号和坐标数字；这只是可读性检查，不是AI检测结果。
- 将“授权报告、合法配置、获准记忆、拓扑”等正文里的高频技术表达改为“收到的报告、允许的配置、各自经历、地图布局”；内部规格保留必要术语。
- 用一个完整选择解释助手作用，不重复堆叠“协作、创新、反制”等抽象结论。删去暗示求助越多必败的表述。
- 概念图和路线图改用中文名称；摄像头位置用无方向的圆环符号，避免图标被当成实际扫描朝向。标签移开路线端点和遮挡块。
- 三张框图同步使用统一名称，标清失败、回退、调度及轮次关系。底层地图与原有美术未重新生图或改变。

## 文案不能替代的设计验证

这些问题保留在原型任务里，不以润色视作解决：

1. **助手是否值得讨论**：专属接口说明它能做玩家手操不能做的事，尚不能证明自然语言协作本身有趣，需观察追问和改法是否改变路线选择。
2. **过度依赖的实际代价**：现有机制支持“忽略设备变化会出错”和“同次会话改动有限”，不能推出求助越多必败，也不新增隐形惩罚或全局额度池。
3. **地图与维修平衡**：需要同时验证固定范围、报告时效、移动距离、维修停留和新增设施；地图更大不等于难度已经合理。
4. **十分钟与运行失败**：四轮加等待是否合适、单轮时限、模型超时／非法输出如何继续，均需实测或定规则。当前未偷偷增加超时判负或随机兜底。
