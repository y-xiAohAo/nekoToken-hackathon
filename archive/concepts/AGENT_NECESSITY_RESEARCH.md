# 玩家侧 Agent 必要性：研究与玩法假设（2026-11-11）

> 讨论材料，不是已确定的游戏规格。预赛仍以 `PRELIMINARY_DESIGN_SPEC.md` 为底稿；本文记录需要团队验证的新方向。

## 要回答的问题

仅让 Agent 拿到另一半线索、总结历史，或执行一次专属按钮，虽然可以在规则上强制使用它，却不足以证明 AI 对体验有必要。我们需要让玩家与 Agent 的**委托、修订和审核关系**成为玩家真正要玩的事。

## 初步答案：把 Agent 变成受委托的“规则执行者”

玩家侧 Agent 不只是提出建议或翻译命令，而是在 RESET 时根据玩家用自然语言表达的目标，**主动建议、执行并在后续回合修订一条持续生效的有限条件策略**；游戏程序负责验证和执行。玩家看到现场，决定策略范围、审核其计划，并在执行中发现计划遗漏了什么。世界 Agent 在 RESET 后基于上一轮的公开行为与规则效果，合法调整一项环境条件。

抽象结构：

```text
玩家表达目标和不能接受的代价
→ 玩家侧 Agent 读取规则变化记录，追问/提出条件策略
→ 玩家审核，Agent 提交受限策略
→ 玩家行动，世界按策略和当前规则结算
→ RESET：世界 Agent 改一个条件；已委托策略若未修订则继续生效
→ 玩家观察策略是否仍符合真正目标，要求 Agent 修订
```

这一结构中，Agent 的必要性有两层：

1. **规则必要性**：只有玩家侧 Agent 的接口能提交持续生效的条件策略；玩家直接操作不能跨轮完成这项操作。
2. **体验必要性的假设**：玩家用开放式语言表达目标、偏好和例外，Agent 必须把它们转成可执行策略，并能在世界变化后解释、修订自己的策略。若换成固定菜单或预写对白后玩法仍一样，则体验必要性尚未成立。

## 极简回合，用来检验因果关系

暂以格子中的危险区作**测试符号**，不锁定最终题材或关卡物件：

1. 玩家想无伤到达目标，告诉助手“帮我避开所有危险”。助手建议一条自动规则：“标记为危险的区域，一律禁止进入。” 玩家若直接同意，初期确实更安全。
2. RESET 后，世界 Agent 在预先限定的范围内调整危险区，通往目标的最后一步现在也被标记为危险。原规则继续生效：玩家不会死，却也不能完成目标。
3. 玩家看到最后一步仍有可承受的风险，向助手补充真正的偏好：“前面不能受伤；最后一步允许我自己承担风险。” 助手把规则改为只保护前段。玩家亲自执行最后一步。

受阻的直接原因是**玩家委托了不完整的目标，随后未审核持续生效的策略**；世界变化只是揭示了遗漏。不能宣称这已被验证为有趣，必须测试玩家是否能理解为何受阻、是否有空间修订，以及修改后是否真正形成新的决策。

## 72 小时 Demo 的边界假设

- 单屏、少量离散行动；一种可委托的条件策略；世界 Agent 每次 RESET 只能从少数合法变更中选一项。
- 玩家侧 Agent 读取结构化规则差异与行动结果，经自然语言讨论后提交结构化策略；游戏程序验证全部提交。
- 策略生效范围和世界变化必须可视化；超时使用可解释的备用方案。
- 10 分钟内至少展示一次“宽泛委托有效”、一次“世界变化使其受阻”、一次“玩家纠正目标并修订策略”的完整链条。

## 尚需验证，不能写成已确定方案

1. 这个“受委托规则”是否比固定菜单产生足够不同的讨论和结果？
2. 用户是否能把受阻归因于委托范围，而非世界 Agent 任意作弊？
3. 策略修订是否比直接换一条行动路线更有价值？
4. 玩家侧 Agent 的受控接口怎样接入用户自有 Agent，同时确保评委无需额外配置也能体验？
5. 若团队更重视横版实时手操，这套按步结算的模型是否还合适？

验证方式：用纸面或低保真原型跑 3 个回合；分别比较无助手、固定菜单、可对话 Agent。只有对话 Agent 能产生可观察的策略修订价值时，才把这套机制写成预赛主张。
